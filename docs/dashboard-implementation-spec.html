Implementation spec

Partiqule home dashboard

Replace the home page with a dashboard that answers one question: what's in my home, and what do I do about it. Reference design is in dashboard-mock-v8.html. Read CLAUDE.md before any code changes.

Context

The current home is scan-first: a big "What are you looking at?" card with a recent scans carousel underneath. The scan affordance is duplicated in the bottom nav FAB, and the carousel doesn't earn its space. The new home commits to discovery and intel as the primary intent. Action surfaces inside intel rather than alongside it.

The single biggest data-layer change is treating ownership as its own state. Right now scanning and owning are conflated, so home metrics get skewed by store-aisle scans the user never bought. Every metric on the new home assumes owned-only filtering.

Reference file: Save dashboard-mock-v8.html somewhere in the repo (suggested: docs/dashboard-mock-v8.html). Use it as the source of truth for visual decisions, color tokens, type sizes, and spacing.

Working rules

  • One track per session. Do not bundle.
  • Read CLAUDE.md first. Honor blast-radius rules on App.jsx, server.js, calibration.js.
  • Surgical patches only. No full-file overwrites mid-session.
  • Plan before edit. Show diffs before applying.
  • Pre-push: npm run build && npm run preview browser verification on any frontend change.
  • Commit messages plain English, no special characters or em dashes.
  • Backend changes on Railway reach users immediately. Frontend changes via Capacitor bundled mode require App Store resubmission.

Strategic prerequisite

The dashboard surfaces findings about a user's owned items. Findings depend on calibration coverage. Today's calibration covers colors (Bucket 1), preservatives (Bucket 2), and the start of sweeteners (Bucket 3). Three of the four planned home-finding categories require calibration that does not yet exist.

Sequencing principle: Calibration buildout precedes dashboard implementation. The dashboard ships when its findings can be evidence-backed, not before.

Findings calibration map

What each home finding requires from calibration:

  • Banned in other countries: supported by current calibration. Yellow 5 and 6 EU labeling, Red 3 international restrictions, sulfites EFSA ADI withdrawal, BHA Federal Register active reassessment all map to this finding category. Ready to ship today.
  • Highly processed foods: requires Bucket 6 (NOVA markers). Today's NOVA inference exists in cascade but is not engine-deterministic. Calibration entries needed for enriched flour markers, isolated proteins, modified starches, processing-aid signals.
  • Hormone disruption: requires new bucket for endocrine-active substances. PFAS class, paraben class, oxybenzone, octinoxate, BPA. Currently zero calibration entries.
  • Fertility risks: requires phthalate class (DEHP, DBP, DEP), BPA, certain pesticide entries. Currently zero calibration entries.

Sequencing decision: Path A

Calibration buildout precedes dashboard tracks 4 and 5. The dashboard ships when all four finding categories can be evidence-backed.

  1. Complete Bucket 3 sweeteners (5 remaining entries: sucralose, acesulfame potassium, saccharin, stevia, erythritol)
  2. Bucket 4 emulsifiers and processing aids (lecithin, EDTA, polysorbates, mono- and diglycerides)
  3. Bucket 6 NOVA markers (enriched flour family, isolated proteins, modified starches, gum-class entries)
  4. New bucket for endocrine-active substances (PFAS class, paraben class, oxybenzone, octinoxate, BPA, phthalate class)
  5. Then proceed with dashboard Tracks 1 through 5 in order

Tracks 1 and 2 (rename and ownership state) can ship in parallel with calibration buildout since they do not depend on findings coverage. Tracks 3 through 5 hold until calibration prerequisites complete.

Tracks

Five tracks, recommended in this order. Tracks 1 and 2 are quick wins that can ship in parallel with ongoing calibration buildout. Track 3 is the data foundation. Tracks 4 and 5 are the visible payoff and require calibration prerequisites complete.

Track 1

Rename "shelf" to "home" in user-facing copy

Smallest, lowest risk. Ship first to validate the language change with users before larger work.

Scope

  • Scan flow: the "Add to shelf" CTA becomes "Add to home".

  • Screen titles: "Your shelf" becomes "Items in your home".
  • Empty states: rewrite any "your shelf is empty" copy to "no items yet".

Acceptance

  • No user-visible "shelf" string remains anywhere in the app.
  • All routes and component names continue to work.

Track 2

Ownership state on data layer

Adds an owned boolean to scanned products. Default true on new scans. This is the foundation for accurate home metrics.

Scope

  • Supabase migration: add owned BOOLEAN DEFAULT TRUE to the user scans table (or wherever scan history is stored, check actual schema).
  • Backend: scan endpoints set owned: true by default. Add support for explicit owned: false via "just looking" mode.
  • Backend: new endpoint POST /scan/:id/ownership with body { owned: boolean } for toggling after the fact.
  • Frontend scan flow: small toggle near the scan capture button: "Just looking" vs default "Add to home". Persist preference per session, not per device.
  • Backfill: existing scans default to owned: true via migration. Users can clean up later via the bulk edit screen (Track 5).

Acceptance

  • Schema migration applied successfully on Supabase.
  • New scans show owned: true in the database.
  • "Just looking" toggle visibly persists across the scan flow within a session.
  • Existing scans backfilled to true.
Files
backend/server.js, Supabase schema, frontend/src/App.jsx (scan flow only)
Risk
Medium. Schema change. Test with cache clear.
Track 3

Home data endpoint

One endpoint that returns everything the dashboard needs in a single payload. Cache aggressively. Compute from owned items only.

Scope

New endpoint GET /home-data returns:

{
  homeScore: 4.2,                    // weighted avg of owned item scores
  homeScoreTrend: "down",            // "up" | "down" | "flat" vs last month
  monthlyDelta: 0.4,                 // points improved or regressed
  itemCount: 50,                     // total owned items
  scoreMakeup: {
    clean: 12,                       // owned items scoring 1-3
    watching: 24,                    // owned items scoring 4-5
    swap: 14                         // owned items scoring 6-10
  },
  streak: 8,                         // consecutive days with at least one scan
  todaysSwap: {
    skipProduct: { name, score, category },
    grabProduct: { name, score, category },
    queueRemaining: 14               // total swap-eligible items remaining
  }
}

Acceptance

  • Endpoint returns valid payload for users with at least one owned scan.
  • Empty-state payload returns sensible defaults for users with zero owned items.
  • Cache TTL set so home loads fast (suggest 5 min Redis cache, invalidate on new scan or ownership change).
  • Today's swap rotates daily based on date hash + user ID, so the same user sees different picks across days but the pick is stable within a day.
Files
backend/server.js, possibly backend/scoringCascade.js for helpers
Risk
Medium. New endpoint, depends on Track 2 schema.
Track 4

Findings engine

Backend computes categorical findings about a user's owned items. Plain language, impact framing, with cleaner-swap counts inline.

Scope

New endpoint GET /home-findings returns top 4 findings by severity and relevance:

{
  findings: [
    {
      id: "hormone_disruption",
      severity: "severe",
      count: 6,
      label: "items linked to hormone disruption",
      swapsAvailable: 4
    },
    ...
  ],
  totalFindings: 24
}

Finding types to support at launch

  • Hormone disruption: items containing PFAS, parabens, oxybenzone, octinoxate, etc. (severity: severe)
  • Highly processed foods: NOVA 4 classified items (severity: severe)
  • Fertility risks: items containing phthalates, BPA, certain pesticides (severity: moderate)
  • Banned in other countries: items with ingredients banned in EU, California, or other strict regions (severity: severe)

Backlog of finding types to add over time: forever chemicals (PFAS-specific), seed oils, artificial dyes (Red 40, Yellow 5), high sodium load, sulfates in personal care, fragrance-as-ingredient, microplastic shedders, and others.

Language rules for finding labels

  • Plain language only. No "PFAS," "NOVA 4," "phthalates," "oxybenzone." Those go in detail views, never on the home.
  • Impact-led: tell the user what it does, not what it is. "Linked to hormone disruption" not "contains parabens."
  • "Linked to" framing for any health claim. Never absolute.
  • No medical claims. No "causes cancer." Never panic framing.
  • Three-beat rhythm where natural.
  • No first person.

Acceptance

  • Endpoint returns top 4 findings, sorted by severity then count.
  • Each finding includes a swapsAvailable count derived from the alternatives table.
  • Tap target on each finding leads to a filtered list of those products with cleaner alternatives ready to swap (Track 5 wires this up).
  • Rotation policy: same user sees varied findings across visits if they have more than 4 categories of issues.
Files
New backend/findings.js, backend/server.js for endpoint
Risk
Medium. Heavy ingredient logic. Test against real shelves.

Loading states

The dashboard depends on aggregations that may not always resolve instantly. Loading state design must communicate "structure loaded, content loading" rather than "the app is broken."

Skeleton loader pattern

On home tab navigation, render the dashboard structure immediately with placeholder shapes where data-dependent content will appear. As endpoints resolve, real content fades in to replace placeholders. No layout shift between skeleton and real content.

Renders immediately with no API dependency:

  • Greeting text ("Good morning, Paul" — name from local storage)
  • Date in subline ("TUE, MAY 5")
  • All eyebrow labels ("Worth knowing", "Today's swap")
  • Section structure (cards, dividers, layout)
  • Bottom nav

Renders as cream-colored pulsing skeleton placeholders:

  • Home Score number and trend arrow
  • Streak count
  • Items count and makeup ribbon segments
  • Legend numbers
  • Each finding row (number, text, swaps-available count)
  • Today's swap product names and score pills

Animation specifics:

  • Placeholder shapes pulse: opacity oscillates between 0.4 and 0.7 over 1.5 seconds
  • Real content fade-in: 200ms transition
  • Skeleton dimensions must match real content dimensions exactly so there is no jump when content loads

Cold app launch (separate from in-app navigation)

On cold app launch from device home screen, show a brief branded splash with the Partiqule wordmark before transitioning to the dashboard skeleton. This is the moment to introduce the brand. Only on cold launch, never on in-app tab navigation. Returning users navigating between tabs see the skeleton pattern, not the splash.

Splash specifications:

  • Cream background, centered Partiqule wordmark in forest green
  • Subtle progress indicator below wordmark (single thin bar that fills from left to right)
  • Maximum duration 1.2 seconds. If app is ready before that, transition early. If not ready by 1.2 seconds, transition to skeleton anyway.
  • No tagline, no copy, just wordmark

Cross-cutting notes

Voice and language rules

  • No first person ("I" or "we") in any user-facing copy.
  • No scientific terms on the home. Plain language only.
  • "Linked to" framing for impact claims. Never absolute.
  • Three-beat rhythm preferred ("Skip it. Grab it. Score it.").
  • No em dashes. No hyphens in display text where avoidable.
  • No emojis in headlines or eyebrows.
  • "Items in your home" is the canonical phrasing for what was "shelf."

Performance

The dashboard depends on aggregated data that may take time to resolve. Performance targets distinguish skeleton render time (instant) from full content resolution time (target).

  • Skeleton renders in under 100ms: no API dependency, pure local render. Greeting, eyebrows, structure, bottom nav all visible immediately.
  • Real content begins resolving in under 500ms for cached users: home-data and home-findings endpoints return cached payload quickly.
  • Full content resolves in under 1.5 seconds for cached users on cellular: this is the experience target for returning users with warm cache.
  • First-time users may see longer resolution: skeleton bridges the gap perceptually. Worst-case 3 to 4 seconds acceptable on first home load with no cache.
  • Cold-start scenarios (post-deploy, post-cache-clear): up to 4 seconds acceptable, skeleton masks the wait.

Caching strategy:

  • Cache /home-data and /home-findings aggressively (5 min Redis suggested)
  • Invalidate cache on new scan, ownership toggle, or alternative confirmation
  • Stream findings in if needed so above-the-fold content (greeting, items section) is not blocked by findings computation

Empty states

  • Zero scans: home shows greeting, single CTA encouraging first scan. No empty findings panel. No empty makeup ribbon.
  • One to four scans: show greeting, simplified items section ("Just getting started"), no findings yet ("Findings appear after 5 scans").
  • Five plus scans: full dashboard.
